# 108heros chat wire protocol v2 — retiring Phoenix

> **Erratum, 2026-08-07 — read this before the "What is NOT changing"
> section.** That section's prose says event names "stay exactly as they
> are", but the list that follows it spells them prefix-free (`message`,
> `syncPending`, `typingStart`) while the v1 wire strings had colon prefixes
> (`chat:message`, `sync:pending`, `typing:start`). Both cannot be true. The
> Flutter client hit this first; the ruling is that **the enumeration wins**
> and v2 event names are prefix-free:
>
> | v1 | v2 |
> |---|---|
> | `chat:message` | `message` |
> | `chat:typing` | `typing` |
> | `chat:update` | `update` |
> | `chats:signal` | `chatsSignal` |
> | `sync:pending` | `syncPending` |
> | `chat:activeRooms` | `activeRooms` |
> | `typing:start` | `typingStart` |
> | `typing:stop` | `typingStop` |
>
> Genuinely unchanged: `messageAck`, `messageNack`, `ackConfirm`,
> `readUpTo`, `globalOnline`, `globalOffline`, `heartbeat`.
>
> Two consequences worth stating plainly. Half the names are camelCase now,
> so any comparison that case-folds the inbound event before matching will
> match nothing — match these bytes exactly. And a client that keeps the
> prefixes will still connect and still exchange frames; it will simply
> match none of them, which is the worst failure mode available.
>
> One thing this spec does not cover at all: the per-user event channel,
> addressed `user:<id>:events`. It has no v2 spelling and no join. The
> server keeps no join registry — `PhoenixSession::should_deliver` in
> api-108jobs' `chat_realtime` crate decides delivery by parsing the id out
> of the topic and comparing it to the session's authenticated user — so
> the clients send no join for it and keep the address as-is.

Three codebases speak this and must agree byte for byte. It replaces the
Phoenix channel wire format, which was inherited from an Elixir relay that no
longer exists (removed in api-108jobs #6). Nothing about Phoenix remains: not
the library, not the frame shape, not the `phx_` names.

## What is NOT changing

**Event names stay exactly as they are** — `message`, `messageAck`,
`messageNack`, `ackConfirm`, `syncPending`, `update`, `chatsSignal`,
`readUpTo`, `activeRooms`, `typing`, `typingStart`, `typingStop`,
`globalOnline`, `globalOffline`, `heartbeat`. Payload shapes are unchanged
too. Only the envelope around them changes, plus the three names that were
Phoenix's own.

## The envelope

Phoenix sent a five-element array: `[join_ref, ref, topic, event, payload]`.
v2 sends a JSON object. Fields are explicit, order does not matter, and an
unknown field is ignored rather than shifting everything after it.

**Client → server**

```json
{"ref": "7", "room": "<room-id>", "event": "message", "payload": {}}
```

- `ref` — optional. A client-chosen correlation id, echoed back on the reply.
  Omit it when no reply is wanted.
- `room` — the room id, plain. NOT `chat:<id>`; the topic prefix is gone.
- `event` — one of the names above.
- `payload` — object, event-specific, unchanged from v1.

**Server → client (unsolicited push)**

```json
{"room": "<room-id>", "event": "messageAck", "payload": {}}
```

No `ref` — nothing asked for it.

**Server → client (reply to a `ref`)**

```json
{"ref": "7", "room": "<room-id>", "event": "reply",
 "payload": {"status": "ok", "response": {}}}
```

`status` is `"ok"` or `"error"`. This replaces `phx_reply`.

## The three renamed events

| v1 (Phoenix) | v2 |
|---|---|
| `phx_join` / `phxJoin` | `join` |
| `phx_leave` / `phxLeave` | `leave` |
| `phx_reply` | `reply` |

Accept **only** the v2 names. The v1 aliases are deleted, not deprecated —
there is no third party to keep compatible and leaving them in is how a
protocol quietly stays forked.

## Topic → room

Phoenix addressed a channel by topic string, e.g. `chat:abc123`, and the
server parsed the id back out with `ChatRoomId::from_channel_name`. v2 carries
the bare room id in `room`. Anything that built or parsed a `chat:` prefix
goes away.

## Heartbeat

Unchanged in spirit: `{"event": "heartbeat", "payload": {}}`, `room` omitted.
The server treats **any** inbound frame as proof of liveness, so the heartbeat
is a keepalive for idle connections only.

## Endpoint

`GET /socket/websocket?token=<jwt>` stays exactly where it is, same auth. Only
the frames on it change. Renaming the path as well would mean two changes to
verify at once for no benefit.

## Naming

No identifier in any of the three repos may keep a Phoenix name. Suggested
replacements — match the local style rather than copying blindly:

- Rust: `phx_helper.rs` → `frame.rs`; `parse_phx` → `parse_frame`;
  `phx_push` → `push_frame`; `phx_reply` → `reply_frame`;
  `PhoenixSession` → `ChatSession`; `phoenix_ws` → `chat_ws`;
  `ChatEvent::PhxJoin` → `ChatEvent::Join`.
- Dart: drop the `phoenix_socket` package for `web_socket_channel`;
  `lib/features/chat/infrastructure/phoenix/` → `.../realtime/`.
- TypeScript: drop the `phoenix` npm package; `PhoenixSocketService` →
  `ChatSocketService`, and so on for the rest.

## Compatibility

There is **none**, deliberately. All three ship together; no production
deployment exists to strand. A client on an old build will not talk to a new
server, which is correct and visible rather than silent.
